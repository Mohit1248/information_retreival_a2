# Grading

This document explains what's undisclosed, what's public, and why —
mirroring Assignment 1's approach of keeping some grading parameters
secret to keep the leaderboard measuring what it claims to measure.

## The three tracks, and what's public vs. undisclosed about each

| Track | Public locally? | Undisclosed at grading time |
|---|---|---|
| A — base LM accuracy | Yes, fully. Run `harness/run_harness.py` on the toy or downloaded dev set and read your raw nDCG@10/MAP@10. | The held-out topic set (same as Assignment 1), the held-out set's candidates file (see below), and the whole class's numbers needed to percentile-rank you. |
| B — clean feedback accuracy | Yes, fully. Same script reports your clean-condition (0% noise) nDCG@10. | Same as above. |
| C — drift robustness | Partially. `harness/noise_injection.py` is public and unit-testable — you can and should sweep it locally. | The **grading** noise levels, sampling strategy, and number of perturbed conditions are not released. Do not assume they match `PRACTICE_NOISE_LEVELS` (0.25, 0.5) or the uniform-random contamination model in `noise_injection.py` exactly. |
| Bonus — round-robin | Not computable locally at all — it requires the whole class's submissions. | The full mechanism (below). |

## Where the provided candidates come from

`data/toy/candidates_dev.jsonl` (and the equivalent file released with the
full corpus's dev topics) is generated by an undisclosed reference
retriever — a straightforward, unremarkable first-pass ranker; its
strength is deliberately unremarkable, since the whole point of this
assignment is what you do with its output, not how good it is. Its exact
method and parameters are not released, for the same reason Assignment
1's baseline parameters weren't: a reranker built around assumptions
about one specific first-pass score distribution or recall profile is
measuring its ability to guess the generator, not its robustness to
realistic candidate quality. Build `score_candidates()` and
`relevance_model_feedback()` to work well given *whatever* candidate pool
they're handed, not tuned to this generator's particular quirks.

The held-out topic set's candidates file is generated the same way but
never released at all — same secrecy tier as the held-out topics/qrels
themselves.

## Why the grading noise recipe is undisclosed

If the exact noise fractions and sampling strategy were public, the
optimal strategy would shift from "build a genuinely robust relevance
model" to "build a relevance model that happens to do well at exactly
those fractions, drawn exactly that way" — which is a narrower, less
useful thing to have built, and not what Track C is trying to measure.
This is the same reasoning Assignment 1 applied to its held-out topic set
and baseline parameters (see that assignment's docs and Section 7).
Build against a *range* of noise levels and think about *why* your
approach is or isn't robust, rather than tuning against the one public
recipe.

## Conformance checks specific to this assignment

Beyond the standard signature/output-format checks (see
`docs/SUBMISSION_INTERFACE.md`), grading runs two checks specific to this
assignment's design:

- **Candidate-pool containment**: every doc_id `score_candidates()` or
  `relevance_model_feedback()` returns must be present in the
  `candidate_doc_ids` it was given for that call. Returning anything else
  (including a doc_id from `pseudo_relevant_doc_ids` alone) is a
  conformance failure.
- **Call-order independence**: `relevance_model_feedback()` is called at
  least once per query with a pseudo-relevant set that is NOT derived
  from your own `score_candidates()` output at all (a harness-constructed
  set built from a different reference ranking). This exists to catch
  exactly the call-order-dependence failure mode described in
  `docs/SUBMISSION_INTERFACE.md` — a submission that quietly assumes its
  seed input always came from its own first-pass reranker.

## Wall-clock budget

`prepare()`: 60 seconds on the toy set, 10 minutes on the full assignment
corpus (this is a one-time collection-statistics pass, not per-query —
see `submission/lm_utils.py`). Each `score_candidates()` or
`relevance_model_feedback()` call: 5 seconds regardless of corpus size,
since every call is scoped to a candidate pool of at most ~100 documents,
never the whole corpus. These are generous — a correct, unoptimised
implementation should not be close to either limit. Exceeding a call's
budget scores that call as a miss (0 on every metric for that query), not
a grading run failure; it does not block the rest of the class's grading
run.

## The bonus round-robin, mechanically

Run once, by course staff, after the deadline:

1. Every team's optional `submission/adversarial_set.json` (a mapping of
   a handful of dev query IDs to a hand-picked pseudo-relevant doc-id
   list) is collected.
2. For every ordered pair of teams (attacker, defender) with attacker ≠
   defender, the harness calls **defender's**
   `relevance_model_feedback(query, attacker's_doc_ids, candidate_doc_ids, k)`
   for each query in attacker's adversarial set — reranking the SAME
   candidate pool defender would normally see, just seeded with
   attacker's poisoned doc_ids instead of defender's own clean top-k' —
   and measures the nDCG@10 drop relative to defender's own
   clean-condition score on that query.
3. A team's **attack score** is the average drop it induced across every
   defender it was tested against. A team's **defense score** is
   `1 - (average drop induced in it by every attacker)`.
4. `instructor-tools/round_robin_bonus.py` combines attack + defense into
   one raw number per team and `harness/leaderboard.py::bonus_component()`
   percentile-ranks that into the `[0, 0.10]` bonus range (assignment
   Section 7).

A team that does not submit `adversarial_set.json` simply is not scored
on this track — no penalty, no entry in the bonus dict, `+0.0`.
